# ExecPlan：已有下载文件冲突提示

## 摘要

下载已下载过的漫画或章节时，不再静默跳过本地文件。在加入队列前异步检查所选章节的输出目录；发现已有页面时只弹出一次确认，让用户选择覆盖重新下载、保留已有文件并补全缺失页面，或取消。

同时修复批量失败假重试，并针对拷贝漫画出现空目录、HTML 404 或限流响应的场景降低章节请求频率。连续站点异常时暂停并保留后续队列，避免把一次风控扩大为整批失败。

参考 `elboletaire/manga-downloader` 的并发分层、单页重试、输出冲突规避和内容格式处理思路，但不复制其 AGPL-3.0 源代码。本次保持 MangaGlass 当前文件夹输出、站点策略及队列模型，只实现适合 macOS 图形界面的冲突决策。

## 用户价值

- 重新下载前明确知道本地已有内容，避免“点击后没有网络请求”却不知道原因。
- 批量选择时只确认一次，不会对每张图片连续弹窗。
- 可选择完整覆盖，也可继续沿用现有断点补全能力。

## 范围

范围内：

- 选中章节加入队列前，在后台扫描实际输出目录。
- 提供“覆盖重新下载”“保留并补全”“取消”三种操作。
- 覆盖策略随队列任务持久化；开始章节时只清理对应章节目录一次。
- 已完成、失败或取消的旧队列记录允许由首页重新加入；正在排队或下载的同一任务仍去重。
- 修复批量“重试失败”先去重、后删除旧记录造成的假重试；失败记录被移除前必须成功创建替代任务。
- 拷贝漫画章节解析请求使用独立的全局节拍与随机抖动，降低章节并发；连续异常触发批次暂停和冷却。
- 入队按钮在扫描期间显示稳定的处理中状态。

范围外：

- 本次不新增 CBZ、图片转码、文件名模板或站点支持。
- 不自动覆盖，不删除未选章节或整部漫画目录。
- 不改变现有重试次数和并发上限。
- 不增加总并发上限；拷贝漫画的实际章节并发会下调。

## 已确认事实

- 当前 `downloadImage` 遇到目标文件已存在时直接返回，界面没有说明。
- 已保存图片采用原子写入；异常退出后重试会自然跳过完整页面。
- 当前队列去重包含已完成、失败和取消记录，导致首页再次下载同一章节时可能只显示“已在队列中”。
- 批量 `retryFailed()` 在旧失败任务仍存在时调用 `add`，新增任务被 `queueIdentity` 去重；之后又删除旧失败任务，造成界面失败项消失但没有实际重试任务。
- 参考项目按章节和页面分别限制并发，单页提供递增延迟重试；输出重名时创建版本化名称，并支持 CBZ／原始目录和 AVIF 转 JPEG。
- MangaGlass 图片请求已有共享节拍，但多个拷贝漫画章节会并发调用 `fetchImageURLs`，章节解析层没有独立节拍；站点返回异常后也没有针对整批 Copy 任务的软熔断。

## 实施计划

1. 提取与下载器一致的章节输出路径计算，供后台冲突扫描复用。
2. 增加可向后兼容的文件处理策略，并写入紧凑队列快照。
3. 实现异步预检查与三选一提示；实际新增后沿用清除选择和入队反馈。
4. 覆盖下载时在工作线程清理对应章节目录，并立即把任务策略改回“保留”，确保异常退出后从新下载的部分继续。
5. 调整队列去重，只替换已结束的同一任务，保留活动任务去重。
6. 修复批量失败重试的替换顺序，并验证重试后存在同数量的新排队任务。
7. 为拷贝漫画增加章节级全局节拍、随机抖动和连续异常软熔断；后续任务回到排队状态，用户继续时遵守冷却时间。
8. 增加路径、冲突统计、策略持久化、覆盖清理、批量重试和熔断边界测试；构建、安装、验收并提交。

## 验证方式

- 已有章节目录含多张图片：弹一次提示，文件数和章节数正确。
- 选择“保留并补全”：已有页面不改写，只下载缺失页。
- 选择“覆盖重新下载”：只删除所选章节目录，随后重新下载。
- 选择“取消”：不增加队列，保留选择和文件。
- 活动任务重复加入仍去重；已完成记录可重新加入。
- 退出恢复后保留覆盖决策；覆盖清理完成后恢复为补全模式。
- 运行完整逻辑测试、27 张布局快照和发布构建。

## 风险

- 输出目录层级取决于同一漫画是否包含多个分组；扫描必须与下载器使用同一个路径函数，避免误判。
- 覆盖属于破坏性操作，删除范围必须限定到明确选中的章节目录。

## 决策记录

- 决策：默认按钮为“保留并补全”，覆盖按钮使用破坏性角色。
  原因：断点补全最安全，也符合当前已有文件跳过逻辑。
- 决策：按一次入队操作汇总冲突后提示一次。
  原因：逐页或逐章节弹窗会阻塞批量下载且难以操作。
- 决策：拷贝漫画章节并发由 4 下调为 2，章节解析请求间隔采用带抖动的保守节拍；图片并发保持现有共享限速。
  原因：当前问题发生在卷／话目录及章节解析阶段，单纯降低图片并发无法阻止章节接口突发请求。
- 决策：连续异常时采用可恢复的软熔断，不自动高频重试。
  原因：风控期间继续请求会制造更多失败；保留队列等待用户稍后继续更可靠。

## 意外发现

- 批量“重试失败”存在确定的数据流错误：去重发生在删除旧失败记录之前，因此旧记录消失不代表已开始重试。
- 用户现场的失败详情是站点返回的 HTML 404 页面，而不是图片文件写入失败；同一漫画网页随后也不再显示卷／话，符合镜像异常或风控期间返回替代页面的表现。
- 仓库追踪了旧路径生成的 `.build` 缓存，直接运行默认 `swift test` 会触发 Swift 模块缓存路径冲突；清理工作区缓存后测试通过，后续验收使用独立 `--scratch-path` 避免污染仓库构建产物。

## 结果与回顾

- 首页加入队列前会在后台检查所选章节目录。发现已有文件时可选择“保留并补全”“覆盖重新下载”或“取消”；覆盖只删除明确选中的章节目录，策略可随队列恢复。
- 同一活动任务继续去重；已完成、失败和取消的记录可以被真实替换。批量重试会先替换终态记录，再创建新的 UUID 排队任务，不再出现失败项消失但未下载。
- 拷贝漫画章节并发由 4 降为 2，所有章节图片列表请求共享 `650–1050 ms` 的随机节拍。429／503／明确风控立即冷却 20 分钟；连续 3 次 HTML 404、空章节或镜像异常冷却 5 分钟。熔断时保留未完成队列，并在队列页说明原因和剩余时间。
- HTML 错误页不再把整段源码塞进失败详情，改为明确提示站点可能处于风控或镜像异常状态。
- `swift test` 共 23 项通过（1 项快照测试在普通测试中按设计跳过）；独立执行快照验收生成并通过 27 张图。`bash scripts/build_app.sh --install` 成功，`dist` 与 `/Applications` 中两个 Bundle 版本均为 `1.6.1`，安装二进制与构建产物一致。
